# Deploying

Built for Docker platforms — Coolify, Dokploy, Portainer, CapRover, Komodo, or
plain `docker compose`. No SSH and no setup script.

---

## Deploy

Point your platform at the repository. It reads `docker-compose.yml` and runs.

Two containers come up:

| Service | What it is | Reachable from outside |
|---|---|---|
| `platform` | pipeline, dashboard, scheduler | **yes** — attach your domain here, container port 8080 |
| `imagegen` | Chrome + the Google Flow extension + an image job queue | **no** — no published port, no domain |

Attach your domain to `platform` only. `imagegen` sits on an internal Docker
network with no route in from anywhere; the platform is the only thing that can
reach it, and it proxies the parts you need behind the same login.

No environment variables required. Three secrets generate themselves on first
boot:

| Secret | Generated by | Lives in |
|---|---|---|
| Admin password | platform | `platform-data` (and printed to its logs) |
| Encryption key | platform | `platform-data` |
| Image service API key | imagegen | `shared-secret`, which both containers mount |

The image service is the only writer of that last one, which is what stops two
containers starting together from racing to create different keys. The platform
mounts it read-only.

### Get the admin password

It is printed in the container logs on every start until you set your own:

```
┌─────────────────────────────────────────────────────────┐
│  ADMIN PASSWORD (generated on first start)              │
├─────────────────────────────────────────────────────────┤
│  quartz-nectar-violet-6493                              │
└─────────────────────────────────────────────────────────┘
```
xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
Open your platform's log view for the container and search for
`ADMIN PASSWORD`.

To choose your own instead, set `AUTH_PASSWORD` in the platform's environment
variables and redeploy.

### Environment variables

| Variable | Default | Purpose |
|---|---|---|
| `IMAGE_API_KEY` | generated | Shared secret between the containers. Generated into a volume they both mount, so it is not a setting in the UI — set it only when the two halves run on different hosts and cannot share one |
| `AUTH_PASSWORD` | generated | UI password |
| `ENCRYPTION_KEY` | generated | 64 hex chars; encrypts stored credentials |
| `FLOW_PROJECT_ID` | — | Optional here; easier to set in Settings → Images |
| `MAX_CONCURRENT_REQUESTS` | `2` | Parallel image generations. Google's own ceiling is 5 |
| `API_COOLDOWN` | `10` | Seconds between calls to Google. Raise it if you see rate limits |
| `MAX_RETRIES` | `5` | Attempts before an image job is given up on |
| `WATCHDOG_DISCONNECT_GRACE` | `120` | Seconds the browser may stay disconnected before Chrome is restarted |
| `TZ` | `Africa/Algiers` | Decides when the publishing day rolls over |
| `LLM_BASE_URL` | `https://ollama.com` | Shared by every API key |
| `IMAGE_BASE_URL` | `http://imagegen:8100` | Where the platform reaches the image service |
| `PORT` | `8080` | Platform listening port |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error` |

Everything else is either a setting in the UI, wiring inside the container
(ports, paths), or part of the request shape Google sees — which is
deliberately not configurable.

This table is the only place these are written down. They are read once when
the container starts, so there is no point in a settings field for them:
editing one in a browser would look like it worked and change nothing.

### The volumes are the things that matter

`platform-data` holds the database, the encryption key and the admin password.
Deleting it means re-entering every credential.

`imagegen-data` holds the **signed-in Google session** and the job queue.
Deleting it means signing in to Google again by hand through the Browser button.

`shared-secret` holds one generated API key. Deleting it costs nothing — a new
one appears on the next boot.

Back up the first two. The Google session is the slower one to replace.

### The live browser

`imagegen` runs a real Chrome under a virtual display, because the Google Flow
API will not accept a request that was not made by a genuine, reCAPTCHA-scored
browser session. There is no API key that substitutes for it.

The **Browser** button in the top-right corner of every page opens that Chrome,
live, in its own tab and behind the same login as everything else. Use it to
sign in to Google the first time, and again whenever the dashboard warns that
the session has lapsed. Refreshing the tab, checking `chrome://extensions` and
switching Google accounts all work there.

It was previously a second public domain guarded by an eight-character VNC
password. It is not exposed at all now.

## Security

The UI holds every credential and can publish to your live sites, so it is
password-protected. That is what makes it safe to sit behind your platform's
public URL.

- Sessions are HMAC-signed cookies, `HttpOnly` and `SameSite=Lax`, valid 30 days.
- `Secure` is set automatically when the proxy forwards `X-Forwarded-Proto: https`.
- Only `/healthz` and `/static/*` are reachable without signing in.
- `/healthz` returns status only — never credentials.

Let your platform terminate TLS. The compose file publishes nothing to the
host: Traefik routes the domain to the container over the Docker network, and
a `ports:` mapping would put the app on the VPS's public interface over plain
HTTP alongside it.

The `imagegen` container is not password-protected itself, and does not need to
be: nothing outside can open a connection to it. It publishes no ports and has
no domain, and Docker routes inbound traffic to published ports only — so the
platform, which checks the session cookie on every request it serves, is the
only client that can reach it.

It does have outbound internet. That is not optional: Chrome has to reach
labs.google. An earlier version put it on a network declared `internal: true`,
which blocks outbound as well as inbound, and Chrome came up with no DNS at all.

Give it a domain and you undo all of this — do not.

## First-time setup

### 1. Settings (shared by every site)

- **LLM** — base URL, normally `https://ollama.com`
- **LLM API keys** — add each key one at a time. Label plus key; nothing else.
  They all share the base URL above.
- **Images** — the **Flow project ID**. The service URL is already filled in,
  and the API key is not a field: the image service generates it into a volume
  both containers mount, and the platform reads it.

  The Flow project ID must be a **real project id from the Google Flow UI**. It
  is sent to Google with every generation as `clientContext.projectId`; a made
  up value makes each request look unlike one the Flow UI would send. Open a
  project in Flow and take the id from the URL.
- **General** — timezone
- **Buffer / Telegram** — on/off switches

### 2. Sites (each has its own credentials)

Every site carries its **own** Site API token and **own** Buffer API token,
because the domains do not share accounts. Add them under **Sites → Add a site**:

| Field | Notes |
|---|---|
| Name, Domain | Domain is editable later; renaming keeps the site's history |
| Daily target | Articles per day. 0 means never publish |
| Minimum gap | Amount plus unit — 20 minutes, 90 minutes, 3 days |
| Site API token | This domain's bearer token |
| Buffer API token | This site's own Buffer account |
| Pinterest username | Picks the right Buffer channel when there is more than one |

The Sites list shows an **API** and **Buffer** badge per row, so a missing
credential is visible at a glance rather than at 3am mid-run. Editing a site
and leaving a credential field blank keeps the stored value.

#### Many sites at once

**Sites → Many at once** imports a CSV. Columns:

```
name, domain, status, daily_target, interval_minutes, pin_username,
project_id, auto_publish, paused_reason, api_token, buffer_token
```

Only `domain` is required, and sites are matched on it — importing the same
file twice corrects rather than duplicates. **A blank `api_token` or
`buffer_token` keeps whatever is stored**, so a file without them changes the
settings and leaves the credentials alone.

Two exports:

| | Contains | Use |
|---|---|---|
| **Export sites** | everything except the tokens (those columns are present and empty) | the default — safe to edit, share, keep in git |
| **Export with credentials** | the same, plus every token in plain text | moving to another deployment, or an offline backup |

The second one is a file that can publish to all of your sites. It does not
belong in a shared folder, a chat message, or a repository. It is logged as a
warning when downloaded.

### 3. Keywords

**Keywords → Download template** gives you a CSV already containing a column
for every site you have added, plus example rows showing `go` / `done` / `no`.
Fill it in, then import it with the button beside it.

### 4. Test

**Dashboard → Dry run** writes a whole article and stops before publishing, so
you can read it without a live site finding out first. It works with automation
still switched off.

When you are happy with it, **Run once now**, then turn automation on.

## Day to day

### Why is nothing publishing?

Two places answer that, from opposite ends:

- **Dashboard → Decisions** — one scheduler check, every site and keyword it
  looked at, with the reason recorded at the moment the choice was made.
- **Keywords → click a keyword** — that keyword against every site, why it is
  blocked on each, and how long the first one has left to wait.

### Articles that wait for you

A site set to **hold every article for approval** (Sites → Publishing) stops
the run after the article is written. Nothing reaches the site until you read
it. Held articles appear at the top of the dashboard under **Waiting for you**.

Opening one shows the article as prose rather than JSON, flags it if this site
already has a near-duplicate title, and offers three things: approve and
publish, edit it first, or discard. Approving is a resume, so every completed
step is reused — it costs one HTTP post, not another pipeline.

Discarding puts the keyword back to `go`, so it will be written again.

### Failures that fix themselves

Failures that look transient — a rate limit, a timeout, the image service
restarting — are retried automatically after a delay that doubles on each
attempt. Failures that would repeat identically — a wrong token, a rejected
payload, a model that does not exist — are left for you, because retrying them
wastes a publishing slot and buries the real error.

Settings → Retries controls it.

### Pausing a site

Sites → open a site → **Pause**, with a reason and a duration. The reason is
shown next to the site everywhere, and the pause lifts by itself when its time
is up. A pause with no end stays until you resume it.

### Prompts and models

Settings → Prompts & models. Each prompt has:

- the text, edited in place, with the shipped version always available
- the last 20 saves, with a diff against what is live, restorable
- the model it is sent to

The model has nothing to do with API keys: any key can serve any model. Keys
spread a rate limit; this decides quality.

### What a run cost

Open any run. Each step shows the tokens it spent and the images it generated,
taken from what the provider reported on each completion, with a summary across
the whole run at the top.

### Notifications

Settings → Telegram. Messages are sent when something *changes* and needs you:

- the keyword queue running out, and refilling
- a site failing its last two runs in a row, and publishing again
- image generation going down, and coming back
- articles waiting for approval

Each is sent once per change, never on a timer, so the channel stays worth
reading.

### History, backups and clearing up

Settings → History & storage:

- counts for every table that grows forever
- a CSV export beside each clear, and cutoffs of 7 / 30 / 90 days or all
- **Download the database** — the whole thing in one file, written with
  `VACUUM INTO` so it is consistent. Site tokens inside it stay encrypted with
  `ENCRYPTION_KEY`, which lives in the data volume and not in that file
- forget shared image sets, so the next run generates fresh pictures
- compact the database after a large delete

### Which model runs which step

Taken from the original workflow and applied by default. Change any of them
under Settings → Prompts & models:

| Operation | Model |
|---|---|
| Spy validation | `gpt-oss:120b` |
| Recipe generation | `gpt-oss:20b` |
| Image prompts | `gemma4:31b` |
| Article parts 1-3 (+ fallbacks) | `gemma4:31b` |
| Pinterest description | `gpt-oss:120b` |
| Board selection | `gpt-oss:120b` |
| JSON repair | `gpt-oss:120b` |

API keys are unrelated to this: any key can serve any model. Keys spread rate
limits; this table decides quality.

### Rate limit behaviour

1. `429` → that key cools down (honouring `Retry-After`) and the **same request
   is retried on the next key**.
2. Three consecutive failures → the key is marked unhealthy and skipped until a
   background check restores it.
3. Only when every key is exhausted does the step fail, naming each one tried.

## Migrating from Google Sheets

Export both sheets as CSV. Import keywords through **Keywords → Import CSV** in
the UI. Keywords → **Export what is here** produces the same columns back, so a
round trip through a spreadsheet works.

For sites, if your platform offers a one-off command:

```bash
node dist/scripts/import-sheets.js --keys KEYS.csv --spy "SPY DATA.csv"
```

Otherwise add sites through the UI — with 5 to 20 of them that is a few minutes.

Credentials are deliberately not imported: they were duplicated across every
row in the old sheet and belong in Settings once.

## Updating

Push to the repository and redeploy. The volume persists, so credentials and
history survive.

### Schema changes

The database is migrated automatically at boot. Before anything is altered, a
copy is written next to it:

```
/app/data/platform.db.pre-migration-2026-08-28T13-40-11-482Z.bak
```

The five most recent are kept. It is written with `VACUUM INTO`, not copied —
the database runs in WAL mode, so a plain file copy silently omits every recent
write.

If the backup cannot be written, the migration does not run and the container
stops with that reason. Doing the risky half of an operation having skipped the
safe half is not a trade worth making.

Each migration runs in its own transaction and is recorded only once it
commits. One that fails rolls back and is not recorded, so the next boot retries
exactly that one rather than skipping it or repeating the ones that succeeded.

Look for these lines in the container log on the first boot after an update:

```
[db] 5 migration(s) to apply: 002-site-pause-and-approval, ...
[db] backed up to platform.db.pre-migration-....bak before migrating
[migrate] applied 002-site-pause-and-approval — A pause with a reason and an expiry
[db] Database ready at /app/data/platform.db
```

Nothing in a migration drops a column, drops a table, or rewrites a row. They
only add. Anything that could lose data belongs in a script somebody runs on
purpose, not in a runner that executes unattended at boot.

### Going back

If an update goes wrong, the pre-migration copy is a complete database. Roll
back by deploying the previous image and putting that file back:

```bash
docker compose stop platform
docker compose run --rm platform sh -c \
  'cp /app/data/platform.db.pre-migration-<stamp>.bak /app/data/platform.db && \
   rm -f /app/data/platform.db-wal /app/data/platform.db-shm'
docker compose start platform
```

Removing the `-wal` and `-shm` sidecars matters: they belong to the database you
just replaced, and leaving them beside a different file is how you get a
corrupt one.

**Settings → History & storage → Download the database** takes the same kind of
copy on demand, if you would rather have one before you start.

## Running locally

```bash
docker compose -f docker-compose.local.yml up -d --build
```

Binds to `127.0.0.1:8080`, bind-mounts `./data` so you can inspect the
database, and mounts `./prompts` read-write for editing without a rebuild.

## Troubleshooting

| Symptom | Cause |
|---|---|
| Cannot sign in | Search the container logs for `ADMIN PASSWORD`, or set `AUTH_PASSWORD` |
| Signed out after redeploy | The data volume was recreated; the cookie key changed |
| `/healthz` lists problems | Credentials missing — Settings |
| API key unhealthy | Bad key, or that account is rate limited |
| `HTTP 401` on fetch-categories | Wrong Site API token for that site |
| Nothing publishes | Automation off, or no eligible pair — see **Decisions** on the dashboard, or open the keyword |
| An article never appears on the site | That site holds articles for approval — see **Waiting for you** on the dashboard |
| A run says "cancelled" | It was held for approval or was a dry run; nothing failed |
| Only one article, then stops | Expected: daily target or interval reached |
| "browser is not signed in to Google" | Open **Browser** and sign in. The session lapsed |
| "Image service unreachable" | `imagegen` is restarting. Chrome takes about a minute |
| Images fail with no useful error | Check credits on the Flow account, and that the Flow project ID is real |
| The browser view is blank | Chrome has not finished starting; reload after a minute |

**Decisions** — a section of the dashboard — answers "why did nothing happen?":
every site checked and every keyword skipped, with the reason recorded when the
choice was made. To ask it about one keyword instead, open that keyword.
