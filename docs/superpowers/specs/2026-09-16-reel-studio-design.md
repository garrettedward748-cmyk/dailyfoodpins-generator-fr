# Reel studio — design

Branch: `ui` (on top of `FB-reels`). Date: 2026-09-16. Agreed 2026-09-16; the clip request was captured the same day (see Stage 3).

## Goal

A published article becomes a **15–60 second, multi-scene reel** with a
presenter the operator created once — face and voice — and a storyboard
written fresh for every recipe, with no person in the loop and nothing the
operator has to understand about Flow, media ids, or ffmpeg.

Every installation starts empty. There is no built-in character. An operator
creates their presenter for their own server, and it is theirs.

This replaces the one-shot reel (one prompt → one 8-second clip) that
`FB-reels` shipped. Everything downstream of the video — page per niche,
caption, link in the first comment, Facebook publishing — stays as it is.

Nothing in this design is provisional. Each stage is built once, complete,
tested, and fit for production; there is no interim mode written to be
replaced later.

## What the operator sees

Three places, and nothing else changes for them.

**Setup → Presenters.** A list of presenters (empty at first). A presenter is
a **character and a voice in the Flow project** — Flow is where both are
made and kept, as two separate assets. Adding one: the operator creates the
character and its voice in Flow through the Browser page, then pastes each
one's id here — it is the long code at the end of the address bar on the
character's page — under a name, with a short description of how they sound
("warm, unhurried, mid-thirties"), which every scene repeats so the delivery
stays the same. Any number of presenters; each Facebook page
picks one (or none: reels on that page are dish-only).

**Setup → Reels.** The style: how long a reel should be (15 / 30 / 45 / 60
seconds; default 30), which *formats* are allowed (below), and whether
scenes are filmed from the article's own images (default) or from fresh
images made for the reel. Sensible defaults, so nothing needs touching to
get started.

**Content → Reels.** One row per reel. Opening it shows the storyboard: each
scene with its source image, its clip, its line, and its status; a retry
button on any scene that failed; and the finished reel. This is also where
"Make a reel by hand" from an article still lives.

Home's *Needs you* list gains: "Page X has no presenter" (informational — a
page without one still gets dish-only reels).

## How a reel is made

Five stages, each a checkpoint, each retryable on its own.

```
plan → (scene images, only in fresh mode) → scene clips → assemble → publish
```

There is no speech stage. Speech is generated by Flow inside each clip: the
scene's line is written into the clip prompt as the presenter's dialogue,
the presenter's voice asset rides along in the request, and the model voices
the line in that voice, in sync with the mouth — which no external voice
track can do.

### 1. Plan (LLM, one call)

Input: the article (title, recipe, the four image prompts), the images it
has (four article images and the Pinterest graphic, by role), the
presenter's description if the page has one, the target length, the format
chosen for this reel.

Output, as JSON, validated before anything is spent:

```
{
  "format": "taste-test",
  "hook": "...",                          // the first line, under 8 words
  "scenes": [
    {
      "seconds": 8,
      "sources": ["feature"],             // which article images this scene is filmed from
      "presenter": true,                  // is the presenter in it?
      "image": "…the frame, fresh mode only…",
      "motion": "…what happens in 8 s…",  // prompt for the clip
      "line": "…what the presenter says…" // may be empty: cooking sound only
    }
  ],
  "cta": "Full recipe in the comments."
}
```

Several scenes may draw on the same image with different motion — a close
pour, then a pull-back on the same dish — and that is encouraged: more
scenes from the same material means more rhythm and less sameness, at no
image cost. Three scenes from five images is the default; the plan decides
which, and may use one image twice and another not at all.

Rules the prompt enforces and the validator checks: 2–6 scenes; each scene
10 seconds (the clip length Flow produces); total within the target ± one
scene; every scene names at least one source that exists; at most one line
per scene, short enough to say in 10 s (≤ 22 words); the last scene carries
the CTA; the presenter appears in at least one scene when the page has one,
and never in every scene by obligation.

**Formats** are what keep reels from all looking the same. The plan prompt is
handed one format per reel and told to follow its shape:

| format | shape |
|---|---|
| `reveal` | close on ingredients → one motion → the finished dish |
| `taste-test` | presenter tastes, reacts, shows the dish |
| `three-things` | "three things that make this work", one per scene |
| `mistake` | the common mistake, then the fix, then the result |
| `pov` | first-person hands only, no presenter |
| `before-after` | raw → cooked, side by side |
| `secret` | "the secret to this one is…" — tease, the thing, the result |
| `countdown` | 3-2-1 over steps or ingredients, one per scene |
| `myth` | "people think… but actually…" — a belief, then the truth |
| `asmr` | no speech at all: cooking sound only, CTA as on-screen text |
| `time-trap` | "ready in 20 minutes" — time as the subject, fast rhythm |
| `first-bite` | opens on the first bite, then back to how it was made |
| `story` | the presenter says why this recipe is theirs, first person |

Thirteen formats. One is picked by rotation per Facebook page — the last four
used on that page are avoided — so a page cycles through every shape before
any comes back. Operators can switch formats off under Setup → Reels.

The prompt lives in `prompts/reel-plan.*.txt`, editable under Setup → Prompts
like every other prompt, with the same versioning. It is written to be
creative on purpose: it is given the format's shape and the recipe's
specifics and asked for a storyboard a food creator would shoot, not a
description of the dish.

### 2. Scene images (fresh mode only)

By default a reel is filmed from images the article already paid for.
Nothing is generated here.

When Setup → Reels says *fresh images*, one image per scene is generated
through the image service exactly as article images are, from the scene's
`image` prompt, with the article's feature image as a reference so the food
matches. This is the only difference between the two modes; everything
after it is identical.

### 3. Scene clips (ingredients to video)

One clip per scene. Every clip is made the same way, with one request
shape: **ingredients to video** — the scene's source image(s) and, when the
scene has the presenter, the presenter's character and voice, handed to Flow
together as references in three separate slots, with the clip prompt. The presenter is therefore
composed into the clip by the model from the first frame, not pasted in from
a still. Scenes without the presenter send the dish images alone.

The clip prompt is assembled from the scene: the motion, then the line as
dialogue in the form the Flow UI itself uses — *the presenter says: "…"* —
then the presenter's voice description, verbatim, the same words in every
scene, as direction for the delivery.

The request shape, captured from the Flow UI on 2026-09-16 (twice: once
with a character and a voice, once with a dish image as well) and pinned by
a test the way `test_request_shape.py` pins the image request:

```
rpcid  MZZa6b                              (not eb1hJf, which is image-to-video)
inner  [[[ [null, null, [[[prompt]]]],
           [[null, <image media id>, null, null, null, <full-frame crop>], ...],  -- slot 1: the scene's images
           "abra_r2v_10s", <aspect: 1 portrait>, null,
           [null, null, null, null, <uuid>, <uuid>], null,
           [[<voice media id>]],                                                  -- slot 7: the presenter's voice
           null,
           [[<character media id>]] ]],                                           -- slot 9: the presenter
        <context(project, captcha)>, [<uuid>, 2]]
```

Three separate reference slots. A scene without the presenter sends null in
slots 7 and 9. The clip is 10 seconds. The worker sends this and nothing
else: there is no image-to-video fallback and no "face from the still" mode.

Clips are generated **sequentially**, with the same pause the article images
use. A failed clip is retried by the image service's own retry; after that it
waits for a person on the reel page.

### 4. Assemble (ffmpeg in the platform container)

- Normalise every clip to the same size, frame rate and codec.
- Concatenate in order, each clip's own sound intact.
- Burn the CTA as text on the last scene (on by default).
- Write one MP4 into `platform-data/reels/<id>.mp4`. The finished file is
  what gets published and what the reel page plays.

ffmpeg is added to the platform image (~100 MB). It is a command, not a
service: it runs for the seconds an assembly takes and exits, so there is
nothing to keep up or shut down between reels. Nothing here talks to Google.

### 5. Publish (unchanged)

The existing engine publishes the assembled file to the page, caption via
`reel-caption`, link in the first comment.

## Data

**`presenters`** (new): id, name, flow_character_id (the character in the
project), flow_voice_id (the voice asset in the project), voice_description,
portrait_url (a copy the platform serves, for the pages), created_at.

**`fb_pages`**: add `presenter_id` (nullable).

**`reels`**: add `plan_json`, `format`, `output_path`. Status set becomes
`planning | imaging | filming | assembling | ready | publishing | published |
failed`.

**`reel_scenes`** (new): reel_id, position, seconds, presenter (0/1),
sources_json (which article images, by role), image_prompt (fresh mode
only), motion_prompt, line, image_job_id, image_url, clip_job_id, clip_url,
status per stage, error. One row per scene is what makes a scene retryable
on its own and the storyboard renderable.

**Settings**: `reel_length_seconds` (default 30 — three scenes),
`reel_formats` (JSON list, default all), `reel_fresh_images` (default off),
`reel_cta_text` (default "Full recipe in the comments").

## Engine

The reel tick already advances reels a stage at a time on its own minute
clock. It grows from three stages to five, still one stage per pass, still
one reel in flight at a time. Each stage reads `reel_scenes`, does only the
scenes not yet done, and moves the reel on when all are. A stage that fails
on one scene marks that scene and stops the reel there; *Retry* on the reel
page clears the scene and the tick picks it up.

Cost guard: a reel is never filmed if the plan has more scenes than the
length allows. It is the one place the reel can be refused, and it says why
on the reel page.

## Not in scope

Voice cloning or any voice made outside Flow. Music. Upscaling. Editing a
plan by hand before it runs (the retry button and the prompt editor cover
what people actually reach for). Multiple presenters in one reel.

## Order of work

0. **Capture the clip request.** Done 2026-09-16: `MZZa6b` /
   `abra_r2v_10s`; images, voice and character each in their own reference
   slot. The request builder and its pinning test come from it. Nothing else
   is captured: a presenter's ids are pasted from Flow's address bar.
1. Presenters: table, page under Setup, two pasted ids and the voice
   description — usable and testable on its own.
2. Plan stage: prompt, validator, formats and rotation; a reel that stops
   after planning and shows its storyboard.
3. Scene clips, per scene, with retry; fresh-image mode.
4. Assemble stage, ffmpeg in the platform image, the reel page playing the
   result.
5. Wire publish; Home notices; settings.

Each step ships complete, with tests, behind the existing "Publish reels to
Facebook" switch, so nothing reaches a page until step 5.
